# Multiphysics requirements: baseline reconciliation

This inventory reconciles [Neural Physical Planner — Multiphysics Specification v1.0, 3 October 2026](SPECIFICATION_V1.md) with the actual `0.3.0` code at commit `3ac1f30337753b1930fc538dc9ac58cbc1ac4c70`. The [unchanged source DOCX](source/Neural_Physical_Planner_Multiphysics_Specification_v1.docx) remains authoritative. The supplied document's v0.2 README snapshot is historical context, not the current implementation inventory. Requirement numbers below retain the specification's numbering.

This is an **M0 requirements audit**, not an assertion that the proposed multiphysics configuration is executable. No M1–M6 gate passes because a similarly named v0.3 feature exists. The earlier four parts passed their bounded software review gates; the reference device pack remains illustrative and has no recorded human photonics review or measured calibration.

Status vocabulary:

- **Partial:** tested support exists for a narrower contract; the full requirement remains open.
- **Missing:** no implementation of the requested contract was found. An adjacent utility or a rejection of unsupported input does not implement that contract.
- **Supported foundation:** a reusable capability described in the inventory below, not a declaration that its containing multiphysics requirement is complete.

“Gate” identifies where the missing work is introduced and subsequently extended. Stage allocation is an implementation roadmap; the exact acceptance criteria remain those of the specification. Tests cited below are existing test definitions and recorded v0.3 evidence, not claims that this document itself executed them. Current M0 verification is recorded separately.

## Staged acceptance obligations

The source specification's stages are cumulative. A failed review blocks expansion into the next stage; fixing a failing test without recording the relevant reviewer judgment does not close a stage.

M1 may start with one analog-electrical or photonic matrix family. The other
classical matrix family still needs the same component-contract review in M2
and an appropriate independent check in M3 before its mixed fixtures and H1/H2
comparisons execute. Existing optical fanout does not satisfy the photonic
matrix-tile requirement. Both classical families remain part of the full scope.

Minimum coherent research release remains open: a complete digital path, genuine mixed computation, storage/timing, evidence-aware accounting, independent semantic checks and a reproducible crossover study are still required. The full initial scope additionally requires five separately expressible families, legal evaluated mixtures, diagnosed unsupported mixtures and executable H1–H6 when their chosen models are supplied. An experiment may validly conclude that a proposed mechanism loses.

## Architectural risks to resolve before M1/M2 coding

1. **Do not widen the fixed intensity union into universal physics.** Preserve its exact schema/evaluator and wrap it as a bounded backend when useful. New contracts should distinguish carrier, regime and encoding without weakening the existing guards.
2. **Do not confuse model transport with neural computation.** The launch source represents a value computed and encoded outside the fanout boundary. A mixed FFN must pay for the previously external operators, encoding, drivers, controls and support; its costs cannot be obtained by adding macro and subcircuit totals indiscriminately.
3. **Do not turn readiness into a scheduler by renaming it.** Shared resources, state lifetimes and clock conversions require reservations and hazards. Source standby, programming and calibration become workload-dependent once time-sharing is introduced.
4. **Preserve provenance without manufacturing evidence.** Grouped citations and SAX agreement do not characterize the numerical parameters. Unknown cost and missing model are first-class outcomes; a component's fidelity and its evidence are independent axes.
5. **Preserve replay meanings while adding backend identity.** Legacy and physical hashes use different canonical JSON policies. Keep both old contracts; a new version must pin evaluator/interface identities and invalidate dependent context deliberately.
6. **Avoid scalar expansion of realistic models.** The current physical limits deliberately bound lanes, fanout, instances, covariance and saved output. New work needs symbolic shapes and tiles, not larger limits applied to one device per model scalar.
7. **Keep independent validation independent.** Current adapter field functions avoid the scalar evaluator, and tests perturb either side to detect agreement bugs. New oracles must retain that separation; a second entry point that calls production formulas adds replay coverage only.
